# فهم المشروع خطوة بخطوة

المشروع يستخدم React وCSS عاديًا وFirebase. الشكل الجيد لا يحتاج كودًا معقدًا: الألوان والمسافات والتجاوب في ملفات CSS، أما JavaScript فيتعامل مع التنقل والبحث والنماذج. لم يتغير التصميم أو الصور أثناء التبسيط، ولم نضف أخطاء متعمدة لجعل الكود يبدو أقل خبرة.

## ابدأ من هذه الملفات

`src/main.jsx` يضع التطبيق داخل AuthProvider. `src/App.jsx` يشغّل BrowserRouter ويغير عنوان التبويب عند الانتقال. `src/router.jsx` يربط كل عنوان بصفحة من مجلد `pages`. اقرأ صفحة الرئيسية ثم صفحة الخدمات؛ ستجد بيانات عادية وروابط وبطاقات تتكرر باستخدام map.

مجلد `components` يحتوي الأجزاء المشتركة مثل Navbar وServiceCard وFormField. نفصلها لأن أكثر من صفحة يستخدمها، لا لإضافة طبقات معقدة. مجلد `services` يحتوي دوال البحث والاتصال بـFirebase. `src/firebase.js` يجهز الاتصال مرة واحدة من متغيرات البيئة. بيانات العرض في `data`، والتنسيق في `styles`، والتحقق في `utils/validators.js`.

## الحالة وأحداث الفورم

useState يحتفظ بقيمة تتغير، مثل نص البحث أو رسالة الخطأ أو بيانات الفورم. عند كتابة قيمة في input، يشغّل onChange دالة `updateField`. تقرأ الدالة اسم الحقل وقيمته، ثم تستخدم setForm لتحديث هذا الحقل مع إبقاء بقية الحقول. علامة checkbox تستخدم checked بدل value. نفس الفكرة مستخدمة في التسجيل والطلب وتعديل الملف.

عند إرسال الفورم، تمنع `event.preventDefault()` إعادة تحميل الصفحة. نفحص المدخلات أولًا، ثم نعرض الأخطاء إن وجدت. إذا كانت البيانات سليمة نستخدم async وawait للحفظ. try يحتوي العملية التي قد تفشل، وcatch يعرض رسالة مناسبة، وfinally يعيد حالة الانتظار إلى الوضع الطبيعي. نجاح الطلب لا يظهر إلا بعد أن تعيد Firebase معرّف الطلب.

## البحث في الخدمات

اقرأ `src/services/servicesService.js`. الدالة filterServices تعمل بثلاث خطوات: اختيار التصنيف، ثم البحث في العنوان واسم التصنيف، ثم ترتيب السعر. filter تختار عناصر من المصفوفة، وfind تبحث عن عنصر واحد، وsort ترتب النتائج. نعمل على نسخة حتى لا نغير ترتيب بيانات العرض الأصلية.

الدالة normalizeArabic توحّد أشكال الألف وتحذف الحركات والتطويل. تعبيرات replace الخاصة بها يمكن شرحها كما هي؛ لا تحتاج تغييرها حتى تضيف خدمة جديدة. رابط البحث يحتفظ بقيم q وcategory وsort، ولهذا تعمل أزرار رجوع وتقدم المتصفح مع الفلاتر.

## الحساب والطلبات

useEffect يشغّل عملًا بعد عرض المكون، مثل تحميل الطلبات أو الاستماع لحالة الحساب. AuthContext يشارك الحساب الحالي بين الصفحات، وuseAuth يقرأ هذه الحالة؛ لا توجد كلمة مرور محفوظة في المتصفح ولا حساب دخول وهمي.

في صفحة طلباتي، RequestList مكون محلي داخل نفس الملف. يأخذ userId، ويُستخدم معه key يساوي معرّف الحساب. إذا تغيّر الحساب، ينشئ React قائمة جديدة بدل إعادة استخدام بيانات الشخص السابق. متغير ignoreResult يمنع عرض نتيجة تحميل قديم بعد إغلاق المكون أو إعادة تحميله. هذه احتياطات بسيطة لكنها ضرورية لحماية الخصوصية.

ملف الطالب يفرق بين AccountProfile الحقيقي وملف مقدم الخدمة التجريبي. البريد والهوية يأتيان من الحساب، ولا يتغيران من فورم تعديل الاسم والقسم. القواعد في `firestore.rules` هي التي تمنع الوصول لبيانات الآخرين؛ إخفاء الزر وحده لا يحمي البيانات.

## ما يمكن تعديله بسهولة

يمكن إضافة خدمة إلى `src/data/services.js` بنفس حقول الخدمات القائمة، ثم فتح صفحة الخدمات للتأكد من ظهورها. يمكن تغيير مسافات البطاقات أو ألوانها من CSS دون تغيير البحث أو Firebase. لشرح فورم الطلب، تتبع updateField ثم handleSubmit ثم createServiceRequest؛ هذه هي رحلة البيانات من الحقل إلى الحفظ.

بعد أي تعديل شغّل `pnpm test` ثم `pnpm build`. اختبارات قواعد Firestore لها أمر مستقل هو `pnpm test:rules` وتعمل على محاكي محلي. نجاح الاختبار لا يعني أن قاعدة Firestore السحابية قد أُنشئت؛ راجع `docs/STATUS_AR.md` للحالة الفعلية.
