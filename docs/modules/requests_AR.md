# وحدة الطلبات

> **حدود المسؤولية الحالية:** أحمد عيد — `alf-2006` يملك تدفق البيانات وخدمة الطلب؛ مريم مصطفى — `mariammostafa123-mm` تملك واجهة النموذج والتحقق وبطاقات الحالة؛ مصطفى أحمد — `ItzFafa` يملك قواعد Firestore والأمان والمحاكي.

هذه الوحدة تعرض نموذج طلب الخدمة وصفحة **طلباتي**، وتتعامل مع Firestore من خلال `src/services/requestsService.js` فقط. لا تُحفظ خانة الموافقة `consent` في الوثيقة؛ فهي قرار واجهة المستخدم، بينما تُحفظ الحقول المعتمدة في العقد: `userId`, `serviceId`, `serviceTitle`, `name`, `email`, `contact`, `details`, `preferredDate`, `status`, و`createdAt`.

## المسارات وحدود التعديل

- `src/pages/ServiceRequestPage.jsx`: ربط الخدمة بالمسار، تعبئة الاسم والبريد من الحساب، حقول النموذج، الأخطاء، الموافقة، ومنع إعلان النجاح قبل نتيجة الحفظ. واجهة الحقول والأخطاء مسؤولية مريم؛ ترتيب الاستدعاءات وتدفق الخدمة مسؤولية أحمد.
- `src/pages/MyRequestsPage.jsx`: التحميل والفراغ والخطأ وبطاقات `pending`/`cancelled` وإلغاء الطلب بعد تأكيد النتيجة. تنسيق الحالة مع مريم وتدفق القراءة والإلغاء مع أحمد.
- `src/services/requestsService.js`: بناء وثيقة الطلب، `addDoc`، استعلام المالك، والترتيب المحلي والإلغاء. لا يقرر صلاحية المالك بدل القواعد.
- `src/utils/validators.js` و`tests/request-form.test.jsx` و`tests/validators.test.js`: التحقق المبكر وتجربة المبتدئ.
- `firestore.rules` و`tests/firestore.rules.test.js`: حدود الملكية والأمان، وتبقى مع مصطفى.

## تدفق الإرسال

1. تُقرأ `serviceId` من المسار ويُستدعى `getServiceById`. الخدمة غير المعروفة حالة عدم العثور ولا تُستبدل بعنصر عشوائي.
2. يملأ المستخدم الاسم والبريد ووسيلة التواصل والتفاصيل والتاريخ، ويؤكد `consent` في الواجهة.
3. `handleSubmit` يستدعي `validateRequest`، ثم يتحقق من مستخدم حقيقي ومن `isFirebaseConfigured`.
4. `createServiceRequest` يبني البيانات من `user.uid` و`service.id` و`service.title` ويضيف `status: 'pending'` و`serverTimestamp()`.
5. لا تظهر رسالة النجاح إلا بعد عودة معرّف فعلي من `addDoc`. أثناء الحفظ يتعطل الإرسال، والفشل لا يغيّر الحالة إلى نجاح.

## السلوك الأمني

كل عملية قراءة أو إلغاء تتطلب مستخدمًا حقيقيًا وتستخدم معرّف الحساب. قواعد `firestore.rules` تمنع قراءة طلبات الآخرين، وتسمح بإنشاء طلب `pending` صالح فقط، وتسمح بتحويل `pending` إلى `cancelled` دون تعديل أي حقل آخر. الحذف ممنوع. الاستعلام يستخدم `where('userId', '==', uid)` ثم يرتب النتائج على العميل، لذلك لا يحتاج فهرسًا مركبًا.

واجهة التحقق لا تغني عن القواعد: طول الاسم والبريد ووسيلة التواصل والتفاصيل والتاريخ يُفحص مبكرًا في `validators.js`، لكن `firestore.rules` تعيد فحص النوع والطول والملكية والوقت والحقول المسموحة. لا تضف `consent` أو حقولًا إضافية إلى الوثيقة دون تنسيق مع أحمد ومصطفى.

## حالات الواجهة

تظهر الخدمة غير المعروفة كحالة عدم العثور. المستخدم غير المسجل يُوجَّه إلى تسجيل الدخول الحقيقي. عند غياب إعدادات `VITE_FIREBASE_*` تظهر رسالة إعداد صريحة ولا تُعرض بيانات وهمية ولا نجاح مختلق. صفحة **طلباتي** تعرض حالات التحميل، الفراغ، الخطأ، و`pending`/`cancelled` فقط. عند تغيير الحساب، تستخدم القائمة `key` يساوي `uid` وتبدأ بقائمة تخص الحساب الجديد.

## الحالة السحابية والاختبار

إعداد SDK ومزوّد Email/Password ونطاق المصادقة مفعّلة حسب الحالة المسجلة، لكن لا توجد Cloud Firestore سحابية منشأة حاليًا، ولذلك لم تُنشر قواعدها ولم يُتحقق من إنشاء الحساب السحابي أو حفظ وقراءة الطلب السحابي. قواعد الطلبات اختُبرت محليًا عبر المحاكي فقط، ولا يجوز إنشاء بيانات سحابية أو حذف رسائل عدم الجاهزية. اختيار منطقة Firestore يحتاج موافقة صاحب المشروع لأنه غير قابل للتغيير بعد الإنشاء.

المحاكي مضبوط في `firebase.json` على `127.0.0.1:8080`، والأمر المقصود هو:

```bash
pnpm test:rules
```

اختبارات الوحدة ذات الصلة:

```bash
pnpm test --run tests/requests.test.js
pnpm test --run tests/requests-account-switch.test.jsx
pnpm test --run tests/request-form.test.jsx
pnpm test --run tests/validators.test.js
```

الحالة المسجلة للمشروع هي 42 اختبار وحدة و10 اختبارات قواعد عبر محاكي CI ناجحة. هذا لا يثبت تنفيذًا يدويًا لطالب ولا نجاحًا سحابيًا.
